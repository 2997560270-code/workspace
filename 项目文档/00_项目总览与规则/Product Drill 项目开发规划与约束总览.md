# Product Drill 项目开发规划与约束总览

## 1. 文档用途

本文用于集中记录 Product Drill 从产品设计、Demo、正式 MVP 开发到后续同步协作过程中已经确认过的规划、规则、约束和执行方式。后续开发必须优先遵守本文，再结合每个模块的专项开发文档执行。

## 2. 项目定位

Product Drill 是一个面向产品思维训练的 Web 应用，核心通过 AI 模拟不同行业客户、用户和产品分析教练，帮助使用者训练以下能力：

- 快速理解不同行业的用户痛点。
- 在不完全明确的客户需求中持续澄清真实问题。
- 针对用户需求输出产品解决方案。
- 评估方案是否真正匹配目标用户、场景、价值和业务指标。
- 分析用户已经做出的自有产品，帮助用户重新理解产品定位、目标用户、真实场景、核心价值和后续优化方向。

## 3. 已确认的方向选择

- MVP 核心方向：B2B、AI+、企业员工培训。
- 第一阶段重点不是做课程，而是做训练工具。
- MVP 不做课程售卖。
- 商业化后期可以探索咨询服务或课程内容，但不进入当前 MVP 主线。
- AI 提问主线是“产品深挖 + 用户需求验证”。
- 自有产品上传分析训练纳入 MVP 核心能力。
- 第一版上传范围以产品资料、文档、源代码文本解读为主；复杂文件解析能力可以后续增强。

## 4. MVP 核心模块

当前正式 MVP 围绕以下模块推进：

1. 首页
   - 简洁介绍项目用途。
   - 展示核心数据和使用方式。
   - 保持高级、简洁、灰白、严肃、低噪音的视觉风格。

2. 训练工作台
   - 选择行业场景、训练模式、难度、训练角色。
   - 用户必须先确认训练设置，AI 才开始输出训练提示。
   - 训练开始后，AI 先询问用户具体业务，再围绕所选场景进行追问。
   - 用户提交方案后，AI 不再继续追问，直接进入评估。
   - 训练过程中切换设置后，必须点击“确定修改”，对话框才更新。
   - 切换场景后要重置追问轮次，并从第一次追问重新开始。

3. 我的产品
   - 产品档案列表在左侧。
   - 中间展示 AI 产品解读。
   - 右侧展示产品成熟度评估与下一步优化。
   - 支持添加产品。
   - 支持上传产品文档和源代码进行 AI 预填写。
   - 支持人工修改产品资料。
   - 支持 AI 先展示对产品的理解，确认后再追问澄清。
   - 支持后续编辑产品资料。
   - 支持删除产品，并支持多选删除。

4. 历史
   - 保存每一次训练记录，不能只保存最新一次。
   - 可查看训练详情、关键对话、AI 点评和评分。
   - 支持重新训练此场景，并带回历史聊天记录方便继续训练。
   - 支持搜索和筛选，包括全部、本周、已评估、待复盘、高价值记录。
   - 历史记录区域固定高度，超出部分使用内部滚动，不让整页失控滚动。

5. 能力画像
   - 基于真实训练记录生成能力表现。
   - 展示平均分、完成训练、最高分、综合进步。
   - 最近训练表现趋势要有坐标轴参数，并突出变化性。
   - 能力维度表现替代原分项能力模块。
   - 高频短板下方增加下一步推荐训练。

6. 使用指南
   - 鼠标移动到使用指南入口时显示。
   - 鼠标移开关闭。
   - 鼠标移动到指南卡片内也可以停留查看。
   - 使用指南卡片出现时，侧边栏不要收回，保持视觉一致。
   - 卡片内可以点击跳转到对应页面。

## 5. UI 与交互总约束

- 正式开发必须严格按照 demov3 的前端模板和视觉风格推进。
- 不允许随意改动 demov3 中已经确认的模块位置和按钮位置。
- 不允许为了实现功能而破坏已经确认的布局结构。
- 侧边栏采用动态收缩设计：
  - 默认只显示图标。
  - 鼠标移入后展开显示文字。
  - 鼠标移开后自动收回。
  - 使用指南卡片展开时侧边栏保持展开。
- 首页底部要保留适当留白。
- 页面要避免按钮遮挡、内容不完整、底部被覆盖等兼容性问题。
- 在笔记本尺寸和外接显示器尺寸下都要保证可用。
- 页面可以局部内部滚动，但不要让核心操作区因为整页滚动导致难以操作。
- 所有主要操作按钮必须是黑底白字。
- 透明按钮或看不出是按钮的控件必须修复。
- 筛选类按钮要有明显可点击形态，不要像普通文字。
- 训练场景选中后要有明显底色反馈，类似难度选中态。

## 6. 训练工作台交互规则

- 用户未确认训练设置前，对话区只显示“请选择您的训练设置”。
- 用户选择完行业场景、训练模式、难度和角色后，需要点击“确定”。
- 点击“确定”后，AI 显示当前训练设置，并询问用户具体业务。
- 用户回答具体业务后，AI 再开始围绕业务场景追问。
- 用户修改任何训练设置后，按钮从“确定”变为“确定修改”。
- 只有点击“确定修改”后，对话区内容才根据新设置更新。
- 切换行业场景或具体场景后，要给用户明确反馈。
- 切换场景后，追问轮次必须重置。
- 用户点击“提交方案”后，应结束当前训练追问并生成评估。
- 训练记录必须保存到历史中。

## 7. 自有产品分析规则

- 用户可以从产品档案列表查看产品。
- 点击添加产品后进入产品资料填写页面。
- 产品资料支持人工填写，也支持上传产品文档和源代码后由 AI 预填写。
- AI 必须先复述它对产品的理解，不直接下结论。
- 用户可以向 AI 说明哪里理解错了，并实时更新理解。
- AI 追问重点包括：真实用户、真实场景、真实问题、替代方案、核心价值、验证指标、风险。
- 产品成熟度评估维度包括目标用户、痛点强度、功能聚焦、数据验证、增长阻碍。
- 优化建议必须分为短期可做、中期验证、长期方向。
- 产品详情中的字段分隔符使用中文冒号“：”，不能出现乱码问号。

## 8. 历史与能力画像规则

- 每次训练提交后都要生成独立历史记录。
- 多轮训练不能覆盖前一次训练。
- 能力画像必须使用真实训练记录计算，不能只显示固定样例。
- 历史详情中必须能看到用户自己的输入和 AI 的回复。
- 重新训练历史场景时，应恢复原有聊天记录，方便继续训练。
- 历史搜索和筛选必须真实可用。
- 筛选按钮需要有明显边框和胶囊样式。

## 9. 开发流程规则

所有正式开发必须遵循以下节奏：

1. 先写当前模块的测试。
2. 运行测试，确认测试先失败，并且失败原因符合预期。
3. 再开发该模块功能。
4. 运行模块专项测试。
5. 运行必要的 E2E 测试。
6. 运行构建验证。
7. 给出手动测试方式和测试入口。
8. 用户人工审核确认。
9. 再进入下一个模块。

补充规则：

- 后续每次开发完都要告诉用户怎么测试。
- 测试入口文件名要体现当前测试模块。
- 后续功能增加后，可以用新的测试入口替换或新增更明确的入口。
- 不要把 demov3 和总验收入口混淆。
- 总验收板块保留，不随意改动。

## 10. 测试与验证规则

- 单元测试用于验证业务逻辑。
- E2E 测试用于验证真实页面交互。
- 构建测试用于确认项目可上线打包。
- 修复 Bug 时要补回归测试。
- 不允许只靠肉眼判断修复成功。
- 视觉类问题如果会反复出现，也要加 E2E 断言。
- 每次声称完成前必须有最新验证结果。

## 12. CodeGraph 使用规则

- `workspace` 中存在 `.codegraph` 时，理解或定位代码前必须先使用 CodeGraph。
- 优先使用 `codegraph explore` 或 `codegraph node`。
- 如果 CodeGraph 返回旧工程索引，要说明正式 MVP 以 `product-drill-mvp` 为准，再继续检查正式项目代码。
- `.codegraph` 文件夹不需要同步飞书云文档，也不需要同步 GitHub。

## 13. 同步规则

- 桌面 `workspace` 是当前本地工作主目录。
- 除本地开发记录外，用户要求同步时再同步到 GitHub 和飞书云文档。
- 本地开发记录只保留在本地，不同步 GitHub，也不同步飞书。
- `.codegraph` 不同步 GitHub，也不同步飞书。
- GitHub 仓库为：

```text
https://github.com/2997560270-code/workspace
```

- 飞书云文档中的共享文件夹名称为 `workspace`。
- 同步前需要注意不要把不该同步的本地记录、缓存、索引、临时文件一起上传。
- 当用户说飞书共享文档被共享者修改后，需要帮助实时同步到本地桌面 `workspace`。

## 14. Git 规则

- 桌面 `workspace` 已做 Git 管理。
- 可以通过 Git 查看历史版本并回退。
- 可以给关键版本打标签，标签名称应能体现版本特性，方便用户识别。
- 不要随意执行破坏性回退。
- 提交前要检查变更范围，避免把旧 demo、临时文件、本地开发记录误提交。
- 用户明确要求 push 时，再推送 GitHub。

## 15. 飞书规则

- 飞书同步使用现有 `workspace` 文件夹。
- 同步前确认文件名和目标文件夹。
- 如果飞书 CLI 上传失败，要先分析原因，不要盲目重复。
- 飞书同步不包含本地开发记录和 `.codegraph`。

## 16. 本地开发记录规则

本地开发记录文件：

```text
C:\Users\A\Desktop\workspace\归纳总结\开发记录.md
```

记录内容只需要包含：

- 踩过的坑。
- 问题原因。
- 解决方式。
- 后续避免方式。
- 对开发有复用价值的经验。

不需要记录：

- 重复性进度汇报。
- 无价值的流水账。
- 每一次普通测试结果。
- 可从 Git 历史直接看出的简单文件改动。

## 17. 当前已经形成的经验

- 中文路径和中文内容写入时要注意编码，避免中文变成问号。
- 之前出现过按钮存在但样式选择器写错元素的问题，例如筛选按钮从 `span` 改成 `button` 后 CSS 仍写 `span`。
- 视觉控件如果“看起来不像按钮”，即使 DOM 存在，也算交互问题。
- 对话输入气泡必须根据用户输入长度自适应，白底黑字，并完整展示用户输入。
- 历史记录必须保存用户输入，不能只显示“你”。
- 页面兼容性要考虑笔记本低高度场景，不能只按外接显示器验证。
- 本地测试入口要能在重启电脑后自动启动本地服务并打开页面。

## 18. 后续开发执行标准

后续每个模块开始前需要明确：

- 本模块目标。
- 本模块不改动范围。
- 需要复用的旧逻辑。
- 需要新增或调整的测试。
- 用户如何手动测试。
- 是否需要同步 GitHub 和飞书。

后续每个模块完成后需要汇报：

- 改了什么。
- 验证了什么。
- 打开哪个测试入口。
- 用户该怎么测。
- 是否已经同步，或者仍然只在本地。

## 19. 当前执行原则

- 优先保证产品闭环可用，再逐步增强智能能力。
- 优先保证交互逻辑正确，再微调视觉细节。
- 优先复用已经写过并验证过的逻辑，不为了重构而重写。
- UI 改动必须贴合 demov3，不破坏既定模板。
- 用户确认后再进入下一模块。
