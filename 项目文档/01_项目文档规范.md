# 项目文档规范

## 1. 目标

建立一套统一、可追踪、可执行的项目文档体系，用于支撑 Product Drill 从 demo 到 MVP 的持续开发。

文档规范要解决的问题：

- 需求来源不清晰，后续开发容易偏离目标。
- 页面和交互修改频繁，缺少版本说明。
- 测试入口多，人工测试时不知道测哪个文件。
- GitHub、飞书、本地 workspace 同步边界容易混乱。
- 开发中踩过的问题没有沉淀，重复排查浪费时间。

## 2. 文档分类

### 2.1 需求与决策文档

存放位置：`01_需求与决策/`

适用内容：

- 用户提出的新需求。
- 人工审核过的方向选择。
- MVP 范围变更。
- 不做范围说明。
- 需求澄清结论。

命名格式：

```text
YYYY-MM-DD_需求名称_需求说明.md
YYYY-MM-DD_方向选择_决策记录.md
```

### 2.2 产品与交互文档

存放位置：`02_产品与交互/`

适用内容：

- 页面结构说明。
- 用户流程说明。
- UI 风格规则。
- 交互状态说明。
- Demo 截图说明。

命名格式：

```text
YYYY-MM-DD_页面名称_交互说明.md
YYYY-MM-DD_UI风格规范.md
```

### 2.3 开发计划文档

存放位置：`03_开发计划/`

适用内容：

- 模块开发计划。
- 测试先行步骤。
- 文件影响范围。
- 技术实现方案。
- 开发顺序。

命名格式：

```text
YYYY-MM-DD_模块名称_开发计划.md
```

每份开发计划必须包含：

1. 开发目标。
2. 不做范围。
3. 涉及文件。
4. 测试计划。
5. 开发步骤。
6. e2e 验证方式。
7. 人工审核方式。
8. 回退方式。

### 2.4 测试与验收文档

存放位置：`04_测试与验收/`

适用内容：

- 每个模块测试说明。
- 打开哪个测试入口。
- 手动测试步骤。
- 自动测试结果。
- 人工验收结论。

命名格式：

```text
YYYY-MM-DD_模块名称_测试说明.md
YYYY-MM-DD_模块名称_验收记录.md
```

每份测试说明必须包含：

1. 测试入口。
2. 测试前置条件。
3. 操作步骤。
4. 期望结果。
5. 异常表现。
6. 通过标准。

### 2.5 发布与同步文档

存放位置：`05_发布与同步/`

适用内容：

- GitHub push 记录。
- 飞书同步记录。
- 本地 workspace 同步记录。
- 协作者打开说明。
- 文件上传范围。

命名格式：

```text
YYYY-MM-DD_同步记录.md
YYYY-MM-DD_发布说明.md
```

### 2.6 版本记录文档

存放位置：`06_版本记录/`

适用内容：

- Git tag 说明。
- 每个版本对应功能。
- 可回退版本说明。
- 重要提交说明。

命名格式：

```text
YYYY-MM-DD_版本记录.md
版本标签说明.md
```

## 3. 单篇文档结构

每篇正式文档建议使用以下结构：

```markdown
# 文档标题

## 文档信息

- 状态：草稿 / 待审核 / 已确认 / 开发中 / 待验收 / 已验收 / 已归档
- 创建时间：YYYY-MM-DD
- 适用范围：说明影响哪个模块
- 关联入口：说明测试入口或页面文件
- 关联文件：列出相关代码或文档

## 背景

说明为什么需要这份文档。

## 目标

说明这次要达成什么结果。

## 范围

### 本次包含

列出明确包含的内容。

### 本次不包含

列出明确不做的内容。

## 方案

说明具体方案、流程或规则。

## 测试与验收

说明怎么验证。

## 风险与处理

说明可能的问题和处理方式。

## 后续记录

记录后续变更、审核结论和补充说明。
```

## 4. 命名规则

### 4.1 文件命名

推荐格式：

```text
YYYY-MM-DD_模块名称_文档类型.md
```

示例：

```text
2026-07-01_训练设置确认流程_开发计划.md
2026-07-01_历史记录内部滚动_测试说明.md
2026-07-01_demov3发布同步_同步记录.md
```

### 4.2 模块名称

统一使用以下模块名称：

- 首页
- 训练工作台
- 我的产品
- 添加产品
- 历史记录
- 能力画像
- 测试入口
- 发布同步
- 项目基础设施

### 4.3 状态命名

文档状态只能使用以下值：

- 草稿
- 待审核
- 已确认
- 开发中
- 待验收
- 已验收
- 已归档

## 5. 内容规则

1. 不使用含糊表达，例如“后面再说”“以后补充”。
2. 需要用户决定的地方，必须写入“人工审核点”。
3. 每个功能文档必须说明“不做范围”。
4. 每个开发文档必须说明“怎么测试”。
5. 每个测试文档必须写清楚“打开哪个文件”。
6. 每次修改测试入口名称时，要同步更新相关测试说明。
7. 影响 GitHub 或飞书的改动，要写入发布与同步记录。
8. 本地-only 内容不得写入 GitHub 或飞书同步范围。

## 6. 本地-only 文件规则

以下内容只保留在本地，不同步 GitHub 和飞书：

- `归纳总结/`
- `.codegraph/`
- 临时截图
- 临时调试脚本
- 含有本地路径、账号、日志的排查文件

本地-only 内容如果沉淀为正式规范，需要整理成脱敏版本后放入 `项目文档/`。

## 7. 人工审核规则

需要人工审核的情况：

1. MVP 范围变化。
2. 页面导航结构变化。
3. 训练主流程变化。
4. 产品分析能力范围变化。
5. 是否同步 GitHub 或飞书。
6. 是否删除旧文件或旧入口。
7. 是否引入新技术栈。
8. 是否改变测试入口名称。

人工审核点必须写成明确问题，例如：

```text
人工审核点：是否把“场景库”作为独立导航保留？
选项 A：保留独立导航
选项 B：合并到训练设置
当前建议：B，原因是减少重复入口
```

## 8. 文档更新规则

1. 开发前：写开发计划。
2. 开发中：发现关键问题，写入测试或开发记录。
3. 开发后：写测试说明和验收记录。
4. 同步后：写发布与同步记录。
5. 用户确认后：把状态改为“已验收”。

## 9. 文档质量检查

提交或同步前检查：

- 文件名是否符合规范。
- 状态是否明确。
- 是否写明测试入口。
- 是否写明不做范围。
- 是否存在含糊占位内容。
- 是否误包含本地-only 信息。
- 是否需要同步 GitHub 或飞书。
